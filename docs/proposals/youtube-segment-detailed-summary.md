# Proposal — Detailed Summary of a YouTube Video Segment for a Tracked Project

**Status:** Draft proposal (scope + example artifacts). No product code in this PR.
**Branch:** `claude/youtube-summary-drafts-uokhjl`
**Author:** MRD platform
**Date:** 2026-06-27

---

## 1. Summary

Add an option to generate a **detailed, downloadable summary of the YouTube video
segment** in which a Tracked Project is discussed — the slice of a Plan Commission
or Council recording that covers that project's agenda item, not the whole meeting.

The output is offered in **three depth tiers** so the same hearing can be consumed
as a quick read or a full record:

| Version | Name | Length | Use it when… |
|---|---|---|---|
| **V1** | Executive Brief | ~½ page | You need the outcome and the "so‑what" in 20 seconds. |
| **V2** | Standard Detailed Summary | ~1–2 pages | You want the full discussion, conditions, and vote — the default. |
| **V3** | Full Deep‑Dive | multi‑page | You need a near‑verbatim record with a complete timestamp index. |

Each version is downloadable as a **Word document** with **clickable `[MM:SS]`
timestamp links** that open the cited moment in the source video.

Three example Word documents accompany this proposal in
[`examples/`](./examples/):

- `examples/v1-executive-brief.doc`
- `examples/v2-standard-detailed.doc`
- `examples/v3-full-deep-dive.doc`

> **Opening them:** these are Word‑compatible HTML files with a `.doc`
> extension — the exact format the app's `askExport` already emits
> (`application/msword`). Double‑click to open in Microsoft Word (or
> right‑click → Open With → Word); the `[MM:SS]` timestamp links are live
> hyperlinks. They are regenerated by
> [`examples/gen_examples.py`](./examples/gen_examples.py).

> **The examples are illustrative drafts.** They are built around one
> representative Indiana residential‑rezoning hearing and are grounded on (a) the
> existing in‑app summary format and (b) the standard anatomy of an Indiana Plan
> Commission / Council hearing. They are **pending validation against the
> 10‑segment research study** described in §5, which is deferred until the live
> backend is reachable from the build environment.

## 2. Background — what already exists

The platform already has most of the machinery for this, but it is currently
**dormant**.

### 2.1 The dormant "Draft Detailed Summary" modal

`index.html` (≈ lines 11556–11650) contains an "MRD Ask" modal whose single
action is **"📄 Draft Detailed Summary"**:

- `window.askOpen(btn)` reads `data-mid` (the meeting/video id, reused as the
  YouTube video id), `data-item` (the agenda‑item title), `data-ord` (ordinance
  number), and `data-sub` (a subtitle line).
- `window.askDraft()` calls the backend `admin_run&fn=draftDetailedSummary`
  with `meeting_id`, `item`, and `ord_number` — i.e. the summary is **already
  scoped to one project's agenda item within one meeting**.
- The response markdown is rendered with `tsLink()`, which turns every
  `[MM:SS]` / `[H:MM:SS]` token into a live
  `https://www.youtube.com/watch?v=<vid>&t=<seconds>s` hyperlink.
- `window.askExport()` serializes the rendered HTML into a **Word‑compatible
  HTML blob** (`application/msword`, `.doc`) — the timestamp links survive as
  real hyperlinks in Word.

### 2.2 Why it's dormant

A comment at `index.html:6300` records that the **per‑project "✦ Detail" Ask
button was removed in P136** ("operator request"). The modal, the draft call,
and the Word export all still exist, but **nothing in the current UI calls
`askOpen`** — there is no entry point. This proposal re‑introduces an entry
point and upgrades the single format to three tiers.

### 2.3 Related summary scaffolding already in the codebase

These confirm the data and patterns the feature relies on:

- **Per‑meeting summary docs** — the Tracked Projects "Youtube Summary" column
  resolves to an AI‑generated summary doc via `_tpFindSummaryDocFor(p)` and
  falls back to the raw YouTube URL (`index.html` ≈ 6261–6305). Hearing records
  carry `youtube_url`, `summary_doc`, `meeting_id`, `date`, `coverage_state`.
- **YouTube‑video Gemini analysis** — `updateMemberVoteHistory` /
  `researchMemberProfile` pass `{ fileData: { fileUri: h.youtube_url } }` to
  Gemini and request **structured, field‑labeled output** (DATE / TOPIC /
  ACTION / DETAIL …). The three‑tier structures in §4 follow the same
  field‑labeled discipline.
- **Word export precedent** — the same Word‑compatible‑HTML approach is used by
  the intel‑briefing export (referenced near `index.html:3280`) and by
  `askExport`. The example `.docx` files in this proposal mirror that styling so
  a future build can reuse it verbatim.

## 3. Goals & non‑goals

**Goals**
- Let a user generate a detailed summary of *the project's segment* of a hearing
  video, on demand, from the Tracked Projects view.
- Offer three depth tiers (V1/V2/V3) chosen at draft time.
- Every tier downloadable as Word, with clickable timestamp links into the video.
- Keep the summary **scoped and grounded** — only this meeting's transcript,
  only this project's agenda item (matching the existing modal's privacy note).

**Non‑goals (this round)**
- No product code is shipped in this PR — proposal and example artifacts only.
- No backend (Apps Script) changes are made here; §6 sketches the options for a
  later task.
- The feature does not re‑summarize the *entire* meeting; whole‑meeting Q&A was
  intentionally removed (P106) and is out of scope.

## 4. The three proposed structures

All three share the same **header block** and the same **source footer**, and all
three use inline `[MM:SS]` timestamp links so any claim is one click from its
moment in the video.

**Shared header block**
- Project name
- Jurisdiction · governing body (Plan Commission / Town Council / BZA)
- Meeting date
- Agenda item / docket / ordinance number
- Segment span (`[start]–[end]` of the project's portion) + video link

**Shared footer**
- Source line: video link + agenda/minutes doc links
- Provenance: "Generated from the meeting transcript by MRD; timestamp links
  open the cited moment in the source video."

### V1 — Executive Brief (~½ page)

Optimized for scanning. Answers "what happened and why do I care" with no
narrative.

1. Header block (compact, one line per field)
2. **Outcome** — one bold line (e.g., *APPROVED 6–1 — favorable recommendation
   forwarded to Council*)
3. **What happened** — 3–5 bullets, each ending with one `[MM:SS]` link
4. **Vote** — one line (tally; "see V2/V3 for roll call")
5. **Bottom line for MRD** — 1–2 sentences on the sales/BD implication
   (timing, builder, lot count, next decision point)
6. **Jump to segment** — single timestamp link to the start of the project's
   portion

### V2 — Standard Detailed Summary (~1–2 pages) — *the default*

The full story of the segment, structured but readable.

1. Header block
2. **Request** — what the petitioner sought (rezone from→to, lots, acreage,
   variances)
3. **Discussion** — narrative with inline timestamps, in hearing order:
   - Staff report / recommendation `[MM:SS]`
   - Petitioner presentation `[MM:SS]`
   - Commissioner / council questions & concerns `[MM:SS]`
   - Public comment (for / against, themes) `[MM:SS]`
4. **Conditions & commitments** — bulleted, each attributed and timestamped
5. **Motion & vote** — motion text, second, roll‑call tally (member‑by‑member
   when the transcript names them) `[MM:SS]`
6. **Outcome & next steps** — disposition + the next body/date if stated
7. Source footer

### V3 — Full Deep‑Dive (multi‑page)

A near‑record of proceedings. Everything in V2, plus verbatim capture and a
complete index.

1. Header block
2. **Chronological timestamp index** — a table: `Time | Speaker / role | Topic`
   spanning the whole segment (the navigational spine)
3. **Request** (as V2, expanded with full legal description / docket detail)
4. **Proceedings** — section per phase with **near‑verbatim, speaker‑attributed
   quotes** for material exchanges, each block timestamped
5. **Public‑comment roster** — table: `Name | For/Against | Key point | [MM:SS]`
6. **Conditions & commitments** — quoted verbatim, attributed, timestamped
7. **Procedural notes** — continuances, recusals, ties, remands, amendments to
   the motion
8. **Motion & roll‑call vote** — full text + member‑by‑member vote
9. **Outcome & next steps**
10. **Appendix** — agenda‑item text, ordinance reference, links to related prior
    hearings for the same project
11. Source footer

### Why these three (depth axis)

A single format always over‑ or under‑serves: a BD lead skimming 40 projects
wants V1; the analyst writing the deal memo wants V2; the person defending a
position in front of a client or building the project's paper trail wants V3.
Same underlying transcript extraction, three render depths.

## 5. Research & validation plan — the 10‑segment study (DEFERRED)

The request was to research **at least 10 real YouTube video segments for
Tracked Projects before finalizing the structures.** That study is **deferred**
because the segment transcripts/summaries live in the Google Apps Script backend
(`script.google.com`), which the current build environment's egress policy
**blocks** (403 on CONNECT), and the repo holds no local snapshot (the
`Data/*.csv` files are sales/market data, not hearings). This section specifies
the study so it can run as soon as the backend is reachable, and so the three
structures above can be validated/refined against real data.

### 5.1 How the 10 segments will be sampled

Pull from `list_tracked_projects_detailed&jurisdiction=*`, then for each
candidate resolve its segment via the project's `meeting_id` + `summary_doc` +
`youtube_url`. Sample for **spread**, not convenience:

| Dimension | Target coverage across the 10 |
|---|---|
| Jurisdiction | ≥ 4 distinct municipalities/counties |
| Governing body | Plan Commission, Town/City Council, BZA all represented |
| Meeting type | Public hearing, continued hearing, and a committee/work‑session item |
| Outcome | Approvals, denials, continuances, and a split vote |
| Segment length | Short (<5 min), medium, and long (>20 min) items |
| Source completeness | Some with `summary_doc`, some video‑only, ≥1 `coverage_state=accept_as_partial` |

### 5.2 What will be extracted from each segment

For each of the 10, record: segment start/end timestamps; speakers and roles
present; presence/absence of each candidate section (staff report, petitioner
presentation, public comment, conditions, motion, roll call); whether a
member‑by‑member vote is recoverable from the transcript; count and density of
usable `[MM:SS]` anchors; and any content that none of V1/V2/V3 currently has a
home for.

### 5.3 How findings tune the three structures

- **Section frequency** → confirm which sections are always present (keep in V1)
  vs. often absent (make optional/conditional in V2/V3).
- **Vote recoverability** → decide whether member‑by‑member roll call is a V2
  field or a V3‑only field.
- **Quote density / length** → set V3's verbatim‑capture threshold so deep‑dives
  stay navigable.
- **Gaps** → any recurring content with no home becomes a new field.

### 5.4 Acceptance criteria

The structures are "validated" when, across the 10 sampled segments: every
present‑in‑transcript fact maps to a defined field in the chosen tier; every
factual line in a generated draft carries a working timestamp link; and V1 fits
on one page, V2 within two, for a typical single‑item hearing.

## 6. Implementation options (for a later task — not built here)

Per decision, only the proposal + examples ship now. Two paths for the eventual
build:

### Option A — Frontend format options (no backend change) *(lower effort)*
Call the existing `draftDetailedSummary` once, then render its structured output
through three client‑side templates (V1/V2/V3), each with its own Word export
that reuses `askExport`. Re‑introduce the entry point as a small control in the
Tracked Projects "Youtube Summary" column (a "✦ Detail ▾" split button offering
Brief / Detailed / Deep‑Dive). **Risk:** depends on `draftDetailedSummary`
returning enough structure to render V3's verbatim/roster sections; may need the
backend to return richer fields anyway.

### Option B — Three backend prompt variants *(higher fidelity, more effort)*
Add three prompt variants to `draftDetailedSummary` (e.g.
`&depth=brief|detailed|deepdive`) so each tier is generated with a purpose‑built
prompt. Best output quality, especially for V3. **Risk:** Apps Script changes
that live outside this repo; 3× generation cost per segment unless cached.

A pragmatic sequence: ship Option A's UI + V1/V2 from the existing call, then add
Option B's `depth=deepdive` prompt for V3 once the §5 study confirms the fields.

## 8. Assumptions & open questions

- **Illustrative content.** The example hearing (Maple Grove, a fictional
  Westfield rezone) is synthesized to show structure; figures are not real until
  §5 validation. The banner in each doc says so.
- **Word format.** Examples are `.doc` (Word‑compatible HTML), the exact format
  the app's `askExport` already emits, so they open natively in Word with live
  links and the shipping feature can reuse the export path verbatim. If we later
  prefer true `.docx`, it's a one‑step change to the export serializer.
- **Open:** Is the three‑tier depth axis right, or should one tier instead pivot
  to an audience/emphasis cut (e.g., a client‑facing version)? Easy to add a
  fourth template once the entry point exists.
